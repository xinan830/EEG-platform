# 设计：按需优先与全量后台补齐

## 1. 核心边界

科学执行模式保持不变：

- `full`：计算指定范围内全部合法窗口并持久化完整 Run artifact。
- `on_demand`：按后端窗口策略确保当前游标目标窗口，结果按窗口持久化。

新增的是离线调度策略，不是第三种科学模式：

- `full_only`：只启动完整 Run。
- `on_demand_only`：只建立按需窗口会话。
- `on_demand_with_background_full`：先服务按需目标，再启动一个独立的完整 Run 在后台补齐。

WPF 可以把这三个值显示为“仅全量分析”“仅按需分析”“按需预览 + 后台全量”。发送给后端时仍分别使用既有 full Run 和 on-demand API。

不支持按需能力的算法不显示组合策略，也不会因为组合策略不可用而自动启动完整 Run；用户必须明确选择“仅全量分析”。

## 2. 启动时序

组合策略的推荐时序如下：

1. 解析并冻结当前记录、导联、通道映射、滤波、算法参数、窗口规则和实际范围，形成一个科学身份。
2. 创建按需会话并立即确保当前游标目标窗口。
3. 当前目标进入终态后，或者用户明确点击“开始后台全量”后，使用同一科学身份提交完整 Run。
4. WPF 同时跟踪 `preview_session_id` 和 `background_run_id`，两个状态不能共用一个 `status`、`progress` 或取消令牌。
5. 用户继续播放或拖拽时，只更新按需目标；完整 Run 保持后台进度。
6. 页面关闭时释放当前订阅，但不自动取消后台 Run；全量任务在全局任务入口中继续可见和可取消。

如果算法不支持按需，组合策略不可选，页面只显示全量任务。若按需服务启动失败，页面可以保留全量任务，但必须显示按需不可用原因，不能静默把全量结果当作当前窗口的按需结果。

## 3. 身份层级与 Prepared Source

组合策略必须分开管理四种身份：

- `ScientificConfigKey`：记录指纹、设备/通道映射、导联/参考、滤波、质量规则、算法定义、科学版本和实现身份。
- `AnalysisPlanKey`：科学配置、完整分析范围、动态窗口长度、步长、全局锚点和算法所需的准备范围/策略版本。
- `WindowKey`：分析计划身份加精确半开样本区间 `[start_sample, end_sample)`、边界策略和窗口 generation。
- `RequestGeneration`：当前 WPF 页面请求代数，只用于防止过期响应污染界面，不得进入任何科学缓存键。

完整 Run 的范围和当前按需窗口的范围不能被当作同一个字段。`actual_range` 描述完整分析计划的实际覆盖范围；具体窗口必须通过 `WindowKey` 单独定位。若算法有全局拟合或长程依赖，窗口相同但分析计划不同也不得自动复用。

每个支持按需或跨模式复用的算法必须声明 `PreparedSourceContract`，至少包含：

- 连续准备的输入范围和有效输出范围；
- 滤波相位/状态、参考方式、gap/边界处理和单位；
- 准备状态（未准备、准备中、可用、失败）及结构化原因；
- 预处理身份、算法版本、实现版本和可验证 artifact/manifest；
- 与完整执行的数值容差和独立对照证据；`numerical_tolerance_evidence` 必须记录
  对照方法及 `rtol`/`atol`，`ready` 状态不得只有一个未经来源说明的裸容差数值。

准备数据不满足契约时，按需执行必须等待准备、返回明确的准备中/不可用状态或走已验证的算法专属路径，不能静默改用局部截窗滤波。

### 5.1 durable single-flight 的所有权规则

同一科学 `WindowKey` 的协调记录必须只有一个活动 producer。producer 负责准备、计算、校验和不可变发布；full 与 on-demand 都是独立 consumer，不因 consumer 数量增加而创建第二个 producer。consumer 订阅包含 `subscription_id`、请求代数、优先级和取消状态，取消只释放该订阅；仅当没有任何活动 consumer、且 producer 尚未进入不可取消的科学计算单元时，才允许协作取消。producer 发生租约过期时由持久化协调点回收并重新排队，旧 producer 不得发布结果。

按需请求可以提升同一 WindowKey 的优先级，但不得改变科学身份或覆盖后台 consumer。full consumer 等待已有 producer 时不得持有计算槽；producer 完成后所有 consumer 读取同一个已校验 artifact。

### 5.2 份额与资源观测契约

协调器必须记录以下字段：`lane`、`window_key`、`wait_ms`、`hold_ms`、`yield_reason`、`cancel_observed`、`resource_rejection_code`、`active_slots`、`rss_bytes`、`cpu_seconds` 和 `temporary_disk_free_bytes`。后台最低执行份额由可配置的交互突发上限和实际 `batch_yields`/`batch_completed` 观测共同定义，不在没有测量前承诺固定帧率或零等待。资源拒绝必须来自结构化预算代码，不能伪装成科学质量拒绝；压力验收至少要证明后台 Run 完成、交互请求不永久饥饿，并报告最坏不可中断工作单元持续时间。

## 4. 调度与资源门

首期使用有限资源预算，不增加无界线程：

- 交互窗口为 P0；后台全量窗口为 P1；未来预取或缓存维护不得高于 P1。
- 按需队列采用最新目标优先和同窗口去重；旧请求可以丢弃，旧响应必须由请求代数和科学身份校验后才能发布。
- 完整 Run 在动态窗口边界检查取消和 `interactive_demand`，在窗口边界让出执行权；不能在 NumPy 计算中强制杀线程。
- 后端共享一个有界科学计算资源门，首期保持单个重计算槽位或由实测决定的固定上限；Native BLAS 线程限制只能有一个进程级所有者。
- 后台任务不得无限饿死：在连续交互压力下也必须获得配置的最低执行份额，并记录每次让出、等待和执行机会耗时。份额和预算由测量确定，不在规格中写死未经验证的数字。
- 调度器必须记录后台单个不可中断工作单元的最长持续时间；窗口边界让出不是抢占式取消，不能对用户承诺零等待。
- 任务失败、取消和资源拒绝必须保留结构化原因，不得转成质量成功或空数值。

当前实现可以复用现有的 batch Run worker 和 dynamic-window worker，但需要增加共享调度协调点；不要再创建一个无界线程池。

## 5. 共享计算所有权、结果来源与缓存

同一 `WindowKey` 的底层科学计算必须支持 durable single-flight：多个消费者共享一个适格的计算和发布结果。每个消费者拥有独立订阅；订阅取消不等于底层计算取消。

当消费者释放时：

1. 先释放消费者订阅。
2. 若仍有后台 Run 或其他有效订阅者，底层计算继续。
3. 若没有有效所有者且任务尚未进入不可取消阶段，才允许协作取消。
4. 已验证发布的结果保留为不可变缓存。

按需与全量必须在同一个共享协调点进行 single-flight 和优先级提升；不能让两个独立 worker 各自根据本地队列判断同窗口是否重复。

结果来源按以下优先级处理：

1. 当前科学身份下已经验证的精确窗口结果。
2. 当前按需目标新计算并通过校验的窗口结果。
3. 当前完整 Run 已发布且可验证的精确窗口结果（仅在该算法具备完整 artifact 窗口索引能力后启用）。
4. 不可用、拒绝、取消或失败结果，保留结构化状态和原因。

当前阶段先保证按需窗口到完整 Run 的复用，PSD 和 STFT 沿用现有验证适配器。完整 Run 反向提供按需窗口需要增加只读窗口索引或可验证的惰性读取，不允许把完整 NPZ 整体加载到 UI，也不允许直接按数组位置猜测窗口身份。

科学缓存身份必须包含：原始记录指纹、科学配置、分析计划、Prepared Source 身份、算法定义和版本、实现身份、采样率、通道/导联映射、参考、滤波、质量规则、窗口策略、参数和实际范围。调度策略、Run ID、订阅 ID、显示缩放、图表选择和 UI 请求代数不进入科学身份。

每个结果同时记录：

- `producer_mode`：最初由 `full` 还是 `on_demand` 产生；
- `result_scope`：单窗口、窗口集合或完整 Run；
- `served_from`：本次由计算、按需窗口 artifact 或完整 Run 索引提供；
- `provenance_id`：指向不可变科学执行证据。

这些字段只追加，不因按需结果后来被 Full Run 复用而改写其最初生产方式。

## 6. WPF 状态与展示

组合策略需要保持以下状态分离：

- `requested_configuration`：用户当前选择的科学参数。
- `preview_target_window`：最新游标目标。
- `preview_displayed_window`：当前已经绑定的窗口及其来源。
- `preview_session_state`：按需会话状态。
- `background_full_run_state`：完整 Run 状态、已完成窗口数、总窗口数和结构化错误。
- `display_projection`：SciChart 选中的通道、频段、缩放和游标显示状态。

当前图表不能因为后台 Run 进度更新而重置游标、播放状态或重复重建 SciChart 数据。后台任务完成一个窗口时，只有当它与当前目标身份和窗口完全匹配，且不会造成旧响应覆盖新目标时，才允许更新来源标识；否则等待下一次导航重新读取。

图表必须显示结果来源，例如“按需窗口”“全量已完成窗口”，并同时保留窗口起止时间、单位、质量和 provenance。后台全量未完成时，不能在导出入口显示“完整结果已就绪”。

## 7. 参数和身份变化

当记录、导联、通道映射、滤波、动态窗口、刷新步数或算法参数变化时：

1. 递增配置代数。
2. 释放当前按需订阅。
3. 停止向旧配置绑定新的窗口结果。
4. 对旧配置的后台 Run 允许继续作为历史任务，也可由用户明确取消；不能把它的进度或结果显示到新配置。
5. 新配置先执行按需目标，再按组合策略启动新的后台 Run。

## 8. 算法能力边界

每个算法继续声明：是否支持单窗口执行、是否支持跨模式复用、预处理范围、窗口边界、质量和取消检查点。支持按需不等于支持 full/on-demand 共享缓存。依赖全局拟合、长程状态或连续预处理的算法必须有独立的准备阶段和数值证据。

首期接入顺序：PSD -> STFT -> 其他已具备能力声明和真实记录证据的算法。FAA 等有独立科学预处理契约的算法不能直接套用 PSD 的缓存实现。

## 9. 失败分类、完整覆盖与恢复

- 按需页面取消、HTTP 超时或订阅释放：当前窗口显示结构化状态；后台全量仍可继续。
- 共享 Prepared Source 损坏、输入非法或算法执行失败：按共享任务故障契约传播到所有依赖消费者，不得伪装成独立的页面失败。
- 全量失败：后台面板显示失败阶段和原因；按需预览仍可继续。
- 页面关闭：释放订阅和轮询，但后台 Run 不因页面关闭而被删除。
- 后端重启：完整 Run 按现有持久队列恢复；动态窗口按 lease/generation 规则恢复或重试。
- 结果损坏：校验失败的 artifact 不可绑定，记录 miss reason 并重新计算。

完整 Run 的 `completed` 必须同时满足：

1. 所有计划窗口均有确定的终态（`Complete`、合法的 `Rejected`、合法的 `Unavailable` 或结构化执行失败）；
2. 每个窗口的状态、质量、原因和有效样本信息均已持久化；
3. 完整 artifact 的范围、窗口索引、数量、manifest 和校验和均通过验证；
4. 不存在仍为 `Queued`、`Running` 或未知状态的计划窗口。

`Rejected` 和 `Unavailable` 可以属于完整覆盖，但不等于有效数值。导出必须保留这些状态，统计必须报告排除窗口及原因，不能静默删除。

Run 创建必须由后端使用稳定幂等身份保护。WPF 的重复点击、页面重建、HTTP 重试和恢复请求不得产生重复活动 Run；用户明确选择“重新运行”时必须生成新的尝试身份并保留旧 Run。

## 10. 取舍与后续扩展

本变更不引入 Zarr/HDF5/Redis/LMDB，也不立即建立完整的 LOD 波形金字塔。先用现有原始读取、SQLite 索引、不可变 artifact 和已验证的窗口复用完成调度闭环。只有测量证明长记录读取或 SciChart 绘制仍是瓶颈时，才建立独立的长记录存储或多分辨率可视化变更。

## 11. 验证策略

验证分四层：

1. 协议层：策略选择、能力回退、配置代数、窗口身份、取消独立性和状态迁移。
2. 后端执行层：交互优先、后台最低份额、同窗口去重、缓存命中/损坏回退、重启恢复和资源预算。
3. 科学层：同一窗口的数值、频率/时间轴、单位、质量和 evidence 对照；连续预处理边界和 gap 单独验证。
4. WPF/人工层：首窗响应、拖拽、播放/暂停、后台进度、全量取消、页面关闭重开、配置切换和导出门禁。

不以单次人工“感觉流畅”定义性能完成；记录首窗延迟、后台吞吐、交互等待、CPU、峰值内存、磁盘和旧响应丢弃数量，并注明测试机器和数据规模。
