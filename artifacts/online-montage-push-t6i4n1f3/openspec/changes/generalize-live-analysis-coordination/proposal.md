# Proposal

## Why

实时 RBP 服务目前同时管理采集会话、窗口步进、样本连续性和算法计算。复制这套服务接入下一个实时算法会重复生命周期与调度逻辑，并增加采集代码对具体算法的依赖。

当前桌面端等算法开启才上传样本，后端从算法开启后重新计窗，因此已经采集了 23 秒时仍需额外等待。采集需要提前保留滚动样本，使 RBP 开启后能直接使用最近 10 秒。

## What Changes

- 新增独立于离线 Run 的实时分析协调能力，统一实时算法会话、窗口调度、样本范围、结果顺序、过载和关闭语义。
- 将 RBP 保留为算法适配器：它声明输入配置并计算给定的实时窗口，不拥有通用会话调度。
- 使用显式算法身份和类型化的通用结果封装；算法特定数值、单位和质量证据仍由对应算法负责。
- 采集会话从第一批样本起维护有界历史。RBP 默认以最新已接收样本为终点请求最近 10 秒，随后每秒更新。结果使用采集会话时间。
- 本次只支持无状态窗口型实时算法。状态型流处理、跨算法依赖、结果持久化和离线协调器复用不在范围内。

## Capabilities

### New Capabilities

- `analysis/live-analysis-coordination`: 实时分析会话与算法无关的窗口调度、样本坐标、并发、结果身份及失败处理。

### Modified Capabilities

- 实时 RBP 启用时机和窗口时间零点随本次补充调整。

## Impact

- 后端实时分析服务、实时采集 API、现有 RBP 测试，以及桌面实时分析桥接契约。
- 不改变 RBP 科学公式、实时身份、输入单位、结果数值或离线算法行为；将同一 RBP 输入在重构前后做契约回归比较。
- 不新增数据库迁移、持久化结果或公开离线 API；现有本地实时消息若需调整，继续使用显式 schema/type 和稳定错误语义。
- 桌面与后端同步更新。沿用当前本地 HTTP 消息结构，明确 `start_s` / `end_s` 为相对采集会话首样本的秒数。原始录制与离线回溯沿用现有链路。
