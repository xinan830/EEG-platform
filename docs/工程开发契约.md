# 脑电分析平台工程开发契约

版本：1.0  
适用范围：`D:/AI/Work/brain-platform` 全部前端、后端、测试、脚本和文档代码。  
技术栈：Vue 3 + TypeScript + Vite；FastAPI + Python；BDF/EDF 离线 EEG 阅图与分析。

## 1. 契约地位与优先级

本文件是项目级工程约束。新增功能、修复问题、重构代码和接入第三方库都必须遵守。

规则分为三类：

- **必须（MUST）**：不满足则不能合并或交付。
- **应该（SHOULD）**：有明确理由时可以偏离，但必须在 OpenSpec change 或当前设计文档中记录原因和代价。
- **可以（MAY）**：按具体实现选择。

当代码、旧文档和口头约定冲突时，优先级为：用户当前明确需求 > 当前 OpenSpec specification > 本契约 > 已批准的当前设计文档 > 旧实现。任何偏离都必须留下可追溯记录。

## 2. 设计目标与不可牺牲的原则

项目的第一目标是让 EEG 文件阅图结果**正确、可解释、可复现**，而不是尽快堆叠界面功能。

以下原则不可牺牲：

1. 数据时间、采样率、通道顺序和单位必须明确，禁止依赖隐含约定。
2. 前端负责交互和展示，后端负责文件读取、信号处理和业务校验；同一规则不得在两端各写一份不同实现。
3. 每一个用户可见结果都必须能追溯到：输入文件、参数快照、算法版本、代码路径和错误信息。
4. 无法判断时必须显式报错或显示“无数据/不可用”，禁止用零值、静默回退或伪造结果掩盖问题。
5. EEG 专业结论与普通 UI 状态分开表达；数值、单位、时间基准和质量状态必须同时可读。
6. 代码优先保持短小、单一职责和容易测试；文件超过阈值必须拆分，不能通过压缩格式或删除换行规避规则。

## 3. 目录与职责边界

### 3.1 后端

```text
backend/app/
  api/          HTTP/WebSocket 路由、请求解析、状态码映射
  models/       API 和持久化数据模型
  services/     用例编排、会话生命周期、文件服务
  processing/   与 EEG 算法无关的处理编排或离线计算
  eeg_core/     EEG 领域算法、滤波、频谱和领域模型
  core/         配置、日志、基础设施
backend/tests/  后端单元、契约、集成测试
```

- `api/` 不得直接读取 BDF/EDF，不得实现滤波或指标公式。
- `services/` 负责调用领域层、组合结果和控制生命周期，不复制算法公式。
- `eeg_core/` 不得依赖 FastAPI、Vue、HTTP 请求对象或文件上传对象。
- 数据模型与业务逻辑分离：模型描述结构，服务和领域层执行行为。
- 一个服务只负责一个用例族，例如导入、窗口读取、波形回放、分析；禁止建立“万能服务”。

### 3.2 前端

```text
frontend/src/
  api/          HTTP/WebSocket 客户端和传输类型
  types/        领域类型与接口类型
  components/   可复用、单一职责的 Vue 组件
  views/        页面级组合组件
  composables/  响应式状态、生命周期和副作用
  utils/        无副作用的纯函数
  styles/       全局和按模块拆分的样式
```

- 页面组件只做状态组合，不直接拼接复杂绘图、请求和数据转换逻辑。
- API 请求只能通过 `api/`，禁止在模板或任意组件中散落 `fetch`。
- 绘图、播放、时间轴、调试采样等状态应分别放入 composable 或独立组件。
- 纯计算放在 `utils/`，必须可在无浏览器环境下单测。
- 一个组件不得同时承担导入、播放、滤波、绘图和报告五类职责。

## 4. 前后端数据契约

### 4.1 时间契约

- 文件绝对时间统一使用 `absolute_time_s` 或明确的 `start_s`/`elapsed_s`，单位为秒，浮点数。
- 调试台输入的秒数**永远是文件绝对时间**，不得自动加当前窗口起点。
- 窗口读取请求中的 `start_s` 是文件绝对起点；返回的 `elapsed_s` 也必须是文件绝对时间。
- `position_s` 是播放游标的文件绝对时间；播放重置必须返回 `0.0`。
- 只有时间轴视窗的 `viewStart`、`viewEnd` 可以是 UI 局部状态，禁止把它们当成文件时间传给后端。
- 秒数比较和样本索引必须明确取整策略：读取起点使用 `floor` 或文档规定的规则，不能在不同接口混用。

### 4.2 EEG 数据契约

- 后端内部原始信号统一为 `numpy.ndarray[float]`，形状为 `(samples, channels)`，单位为伏特（V）。
- API 返回波形值统一为微伏（µV），并在字段或文档中标明；禁止同一接口混用 V 和 µV。
- `sfreq` 为 Hz；`duration_s = sample_count / sfreq`，不得用前端计时器估算文件时长。
- `ch_names` 与样本列一一对应，任何裁剪、排序、通道选择都必须同步更新两者。
- 通道匹配默认大小写不敏感，但返回值使用文件原始通道名。
- 过滤器必须声明低切、高切、陷波和参考方式；参数快照随结果返回或记录。
- 任何重采样、降采样或抽点都必须记录方法、步长和可能的显示误差。

### 4.3 HTTP/WebSocket 契约

- 请求和响应结构使用显式类型；不得返回未说明的动态字典作为公共接口。
- 成功、客户端参数错误、资源不存在、服务内部错误使用稳定的 HTTP 状态码。
- 错误响应至少包含稳定的 `code`、可读的 `message` 和可定位的 `request_id`。
- WebSocket 消息必须有稳定的 `type` 字段；新增消息类型必须更新类型定义、处理分支和测试。
- API 变更遵循“先兼容、再迁移、后删除”：删除字段前必须记录迁移方案和截止版本。
- 前端不得根据错误文本做逻辑判断，只能依据错误码或结构化字段。

## 5. 可追溯性契约

任何问题都必须能够从用户操作追到最终数据或错误。

### 5.1 必须记录的链路

```text
用户操作
  -> 前端动作名与参数快照
  -> request_id / session_id
  -> API 路由与服务用例
  -> 文件标识、时间窗口、通道、滤波参数
  -> 处理步骤与算法版本
  -> 返回结果、质量状态或结构化错误
```

### 5.2 标识与日志

- 每个 HTTP 请求和 WebSocket 会话必须有 `request_id`/`session_id`；日志中始终带出。
- 文件必须使用内部 `recording_id` 追踪，日志可显示文件名但不能只依赖文件名。
- 日志记录事件、状态变化、参数快照和耗时；禁止记录密码、令牌或完整敏感文件内容。
- 错误日志包含异常类型、调用阶段和关键上下文；禁止只打印“失败了”。
- 用户可见错误要简洁；详细诊断留在日志和调试信息中。
- 调试台读取结果必须记录：`recording_id`、绝对秒数、实际采样时间、通道列表、滤波/参考参数。

### 5.3 问题复现记录

每个缺陷至少记录：

```text
问题编号：
环境与提交版本：
文件 recording_id / 文件类型：
复现操作：
输入参数（时间、通道、滤波、参考、速度）：
期望结果：
实际结果：
request_id / session_id：
相关日志或响应：
根因：
修复路径（文件、函数、测试）：
```

## 6. 可解读性契约

- 命名表达业务含义和单位，例如 `window_start_s`、`sample_count`、`values_uv`，禁止 `x`、`tmp`、`data2` 充当长期变量名。
- 布尔值使用 `is_`、`has_`、`can_`、`should_` 前缀；状态使用有限集合，不使用散落字符串。
- 领域常量集中定义并命名，例如 `DEFAULT_HIGH_CUT_HZ`；禁止在业务函数中散落 `70`、`1e6` 等魔数。
- 公式实现旁边必须写明输入单位、输出单位和适用范围；复杂算法必须链接到设计文档或论文来源。
- 前端显示文本和后端字段含义必须一致；“窗口内时间”和“文件绝对时间”不得混用。
- 函数应满足“读名字即可知道作用”；超过一个屏幕或包含多个状态机时应拆分。
- 任何静默降级都必须返回原因字段或日志；不得让调用者猜测是否使用了回退值。

## 7. 注释、文档和类型

- 注释解释“为什么”，不重复“这行代码做什么”。
- 算法注释必须说明：数据单位、采样率假设、边界条件、滤波相位/延迟影响和异常处理。
- 公共函数、服务方法、API 路由和复杂 composable 必须有简洁 docstring/JSDoc。
- 类型是契约的一部分：公共函数参数、返回值、API payload、WebSocket 消息不得使用无约束的 `any`。
- 注释过期视为缺陷；修改行为时必须同步修改注释、README、设计文档和测试名称。
- 不写无效注释、情绪化注释、临时 TODO 或“以后再处理”的空承诺。
- 当前行为和科学契约只在 `openspec/specs/` 定义；已完成变更只在 `openspec/changes/archive/` 留存决策记录。
- `docs/` 只用于当前的人工说明、路线图和验证报告；`docs/archive/` 中的文件只提供历史背景，不能作为实现依据。

## 8. 文件规模与职责拆分规则

### 8.1 分级阈值

- 单个方法以 **20～50 行**为宜；超过 **80 行**必须检查是否混合了校验、状态变更、计算和序列化等职责。
- 业务代码文件以 **400 行为目标软上限**，不是“一超过就禁止合并”的硬规则。
- **401～600 行**：允许保留，但必须在 `docs/code-size-policy.json` 登记评估结论、理由和本次允许的最大行数。
- **601～1000 行**：进入高风险评审。除上述登记外，变更说明必须解释为何暂不拆分，以及后续拆分边界或保持单文件的工程依据。
- **超过 1000 行**：手写代码不得以普通 `keep` 结案；必须登记可执行拆分计划，或使用经过明确审查的 `approved_exception`。自动生成代码可登记为 `generated`。
- 文件物理行数包含代码、注释、模板、样式和空行；不得通过压缩、超长单行、删除必要注释或拆成无职责含义的编号文件规避评审。
- 自动生成文件、锁文件和第三方代码不参与普通业务文件评审，但生成来源必须可追溯，且不得手工修改来伪装生成文件。

### 8.2 登记格式

`docs/code-size-policy.json` 是可执行策略。超过 400 行的文件在 `reviews` 中按路径登记：

```json
{
  "reviews": {
    "backend/app/example.py": {
      "max_lines": 540,
      "decision": "keep",
      "reason": "职责单一，拆分会破坏同一状态机的可读性"
    }
  }
}
```

`decision` 只能是 `keep`、`split`、`generated` 或 `approved_exception`。选择 `split` 时必须提供 `follow_up`；代码增长超过登记的 `max_lines` 时必须重新评审。

### 8.3 后端拆分

- 路由文件超过阈值：按资源或用例拆为多个 router，例如 `recordings.py`、`waveform.py`、`analysis.py`。
- 服务文件超过阈值：拆为“读取/转换”“回放会话”“参数校验”等服务；会话状态单独建类或模块。
- 算法文件超过阈值：拆成预处理、频谱、指标、质量门和结果模型；公共入口保持稳定。
- 不得把测试、CLI、迁移脚本塞进生产模块。

### 8.4 前端拆分

- Vue SFC 超过阈值：按“页面壳、工具栏、调试台、波形、时间轴、设置面板”拆组件。
- `script setup` 超过阈值：将请求/播放生命周期抽到 composable，将纯计算抽到 utils。
- 模板超过阈值：拆成语义明确的子组件，禁止用大量 `v-if` 隐藏职责混杂。
- 样式超过阈值：按组件或功能拆分；禁止使用全局选择器覆盖无关组件。
- 同一状态不得由多个组件各自维护；由页面或 composable 单一持有。

### 8.4 拆分验收

拆分后必须满足：

1. 公共接口语义不变，或有明确迁移说明。
2. 新模块有单元测试或契约测试。
3. 循环依赖没有增加，依赖方向仍为 UI/API -> service -> domain/core。
4. 文件名能表达职责，调用方不需要阅读实现才能理解用途。
5. 拆分没有把共享状态复制成多个不一致副本。

## 9. 状态、并发和副作用

- 前端请求必须支持竞态保护：旧请求返回时不能覆盖更新后的状态。
- WebSocket 必须处理连接、重置、完成、错误和关闭五类状态；关闭页面时释放连接和定时器。
- 后端回放会话必须明确创建、运行、暂停、完成、失败、停止状态及合法转换。
- 修改滤波参数时必须重建滤波状态；若产品规则要求从头播放，前后端都必须把位置重置为 `0.0`。
- 纯函数不得读写全局状态、时间或网络；需要副作用的函数名称和文档必须明确。
- 共享可变数组、缓存和队列必须定义所有权、清空时机和线程安全边界。

## 10. 测试与质量门槛

每次行为变更至少包含与风险匹配的测试：

- 纯函数：边界值、单位、异常输入和典型输入。
- API：状态码、响应结构、错误码和参数校验。
- WebSocket/回放：暂停、恢复、重播、定位、参数变更、完成和断开。
- EEG：采样率、通道顺序、时间绝对值、滤波参数、参考方式和 µV 转换。
- 前端：用户动作触发的请求参数、竞态保护、组件状态和关键显示文本。

交付前必须运行与改动相关的测试；禁止以“本地能打开”代替测试。失败测试必须说明是代码缺陷、环境缺失还是已知限制。

## 11. 变更和审查规则

任何改变用户可观察行为、公共接口、时间、单位、通道、滤波、参考、质量或 provenance 语义的工作，必须先建立一个 OpenSpec change。纯文档或工具整理可以使用 `skip_specs: true`，但仍必须说明范围、迁移、验证和回滚。

每个变更说明必须回答：

1. 改了什么用户行为或数据契约？
2. 根因和证据是什么？
3. 改动涉及哪些模块，为什么放在那里？
4. 是否改变时间、单位、通道、滤波、状态或错误语义？
5. 如何验证，测试覆盖了哪些边界？
6. 是否超过 400 行目标线；评估结论和登记位置是什么？
7. 是否有兼容性、性能、数据安全或医学解读风险？

审查顺序固定为：正确性与数据契约 -> 状态/并发 -> 可追溯性 -> 测试 -> 可读性与文件规模 -> UI 细节。

## 12. 禁止事项

- 禁止在前端重新实现后端 EEG 算法并把两套结果混用。
- 禁止把文件绝对时间转换成窗口相对时间后再假装返回绝对时间。
- 禁止用零线、随机值或上一帧结果掩盖“没有数据”，除非字段同时标明质量状态和回退原因。
- 禁止在一个超大组件/服务中持续追加功能而不拆分。
- 禁止捕获所有异常后只显示通用成功或静默忽略。
- 禁止无测试地修改公共 API、WebSocket 消息或单位。
- 禁止提交真实 EEG 文件、凭据、访问令牌或包含个人身份信息的日志。

## 13. 完成定义（Definition of Done）

一个功能只有同时满足以下条件才算完成：

- 需求、边界和失败行为已明确。
- 前后端职责和数据契约已更新且一致。
- 文件规模符合分级策略；超过 400 行的文件已登记职责评估，超过 600/1000 行时已满足对应审查要求。
- 公共接口有类型，复杂逻辑有清晰注释和文档链接。
- 关键路径有自动化测试，测试结果已记录。
- 日志、错误和 request/session 标识足以复现问题。
- 没有遗留 TODO、临时开关、调试输出或未说明的静默回退。
- OpenSpec change 或相应当前文档已写清根因、证据、影响、验证和风险。

这份契约本身也必须随架构演进更新；若规则不再适用，应提交“修改契约”的独立变更，而不是在代码中悄悄绕过。
