# 文件规模契约改为分级软上限

## 基本信息

- 变更编号：CONTRACT-2026-09-11-SIZE
- 日期：2026-09-11
- 关联问题：400 行硬门禁可能诱发机械拆文件，不能直接证明职责清晰。

## 事实与判断

- 事实：旧检查器在生产文件超过 400 行且无遗留基线时直接失败。
- 判断：行数是复杂度信号，不是职责边界本身。硬切文件可能缩短物理行数，却增加跨文件跳转和隐式耦合。
- 风险：完全取消检查同样不可取，会让超大状态机和多职责模块重新累积。

## 新规则

- 400 行是目标软上限。
- 超过 400 行必须在 `docs/code-size-policy.json` 登记决定、理由和允许上限。
- 超过 600 行给出高风险提示，并要求在变更记录中写清拆分边界或保留依据。
- 超过 1000 行的手写文件不能使用普通 `keep` 决策，必须提供拆分计划或批准例外。
- 方法以 20～50 行为宜，超过 80 行进行人工职责检查；暂不使用不可靠的跨语言自动方法计数。

## 自动化行为

- `backend/scripts/check_file_sizes.py` 从策略文件读取阈值，不在脚本中把 400 行写成提交硬门禁。
- 未登记的超目标文件、超过登记上限的文件、缺失理由或无跟踪项的拆分计划会导致 CI 失败。
- 已评审且未超过登记上限的 401～1000 行文件可以通过，并输出评审提示。

## 验证与风险

- 新增策略检查单元测试，覆盖目标线、允许保留、增长越界、拆分跟踪和超千行限制。
- GitHub Actions 继续执行同一检查脚本，无需修改工作流入口。
- 自动检查只能验证评审记录存在，不能判断理由是否真实充分；代码审查仍必须判断职责内聚性。
